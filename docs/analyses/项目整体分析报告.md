## 一、项目定位

一个**多租户企业知识库问答 Agent**，核心特征是 **RAG + Text2SQL 双引擎**：

| 问题类型 | 处理通道 | 典型例子 |
| --- | --- | --- |
| 条款、政策、规格、流程 | RAG 文档检索 + 引用 | "路由器整机质保多久？" |
| 全量精确统计 | Text2SQL 只读查询 | "Sales 和 Engineering 各多少人，差多少？" |
| 需要两者结合 | Agent 工具编排 | "实际业务指标是否符合制度规定？" |

项目自我定位诚实：**"可演示、可测试的工程实践项目，目前适合受控内部试点，尚未完成生产质量与容量验收"**（README.md:5）。这个定位与代码实际成熟度基本吻合。

技术栈：Python 3.12+ / FastAPI / SQLAlchemy 2.0 async / PostgreSQL / Qdrant / Redis / ARQ / Alembic / sqlglot / jieba；前端 Vue 3 + TypeScript + Pinia + Vite + nginx；部署 Docker Compose。模型默认走 SiliconFlow（DeepSeek-V3.2 + BGE-M3 + BGE Reranker）。

## 三、核心模块实现（代码核对结果）

### 3.1 Agent 编排：手写有界状态机

作者刻意**没有引入 LangGraph 等图编排框架**，理由是"当前只需要三个工具，显式状态机便于复用 SSE 协议、检查状态和测试分支"（README.md:182）。这个取舍在小工具集下是合理的。

**三条执行路径**（`backend/app/agent/loop.py:135-180`，与文档声称一致）：

1. **强制 SQL** — 规则命中 → `_run_forced_sql()`，直接调 `list_data_tables` + Text2SQL，**跳过 LLM 决策，零编排成本**
2. **强制 RAG** — 规则命中文档意图词 → `_run_forced_rag()`
3. **LLM 自主循环** — 规则未决 → `_run_llm_loop()`，function calling 选工具

**规则路由的判定优先级**（`backend/app/agent/router.py:107-169`）设计得比文档描述更细：

- ① 命中 `DOC_WORDS` 且**不是**（聚合词 + 列名词同时命中）→ RAG
- ② 聚合词与列名词**同时命中** → SQL
- ③ 仅命中列名词 → 交给 LLM 决策
- ④ 无信号 → 交给 LLM 决策

亮点在于 ① 的优先级设计：`router.py:136` 注释举例 **"最多多久吃一次"** 同时命中聚合词"最多"和文档词"多久"，若按"聚合词优先"会误路由到 SQL，因此让 DOC 优先。这说明规则表是被真实 badcase 打磨过的，不是拍脑袋写的词表。列名词表还支持从 schema 动态生成（`build_column_words()`，`router.py:172-189`）。

**五重防死循环**（`loop.py:9-14, 43-46, 273-356`）：

| # | 机制 | 位置 |
| --- | --- | --- |
| 1 | `MAX_STEPS = 5` 步数硬上界 | L44 |
| 2 | `WALL_CLOCK_SECONDS = 60` 墙钟超时 | L45, L275-279 |
| 3 | `MAX_LLM_CALLS = 8` 编排调用预算 | L46, L280-284 |
| 4 | `seen_calls` 集合：相同工具 + 相同参数 JSON key 判为循环 | L308-317 |
| 5 | 任一步失败/超步 → **降级到 `_run_forced_rag()` 而非抛错** | L351-356 |

第 5 条是关键的用户体验设计：Agent 失败不会给用户一个 500，而是退回 RAG 并发送 `degraded` 事件。但 README.md:195 也诚实标注了风险 —— **"统计问题降级到 RAG 也不代表仍能精确计算，应按失败/降级场景独立验收"**。这是一个已知但未闭环的缺口。

**SSE 事件契约**（`backend/app/agent/events.py`）：4 类冻结字段的基础事件（`meta` / `delta` / `done` / `error`）+ 6 类扩展事件（`route` / `tool_call` / `tool_result` / `sql` / `clarify` / `degraded`）。"扩帧不改帧"的向后兼容策略与前端"未知事件类型静默忽略"（`frontend/src/stores/chat.ts:327-329`）配套，前后端可独立演进。

### 3.2 混合检索链路

实际流程与参数（`backend/app/vector/qdrant.py:297-411`）：

```
Dense 召回 (BGE-M3, prefetch_k=20)
  + BM25 稀疏召回 (Qdrant 内置 bm25 + jieba 预分词, prefetch_k=20)
  → RRF 融合 (FusionQuery, Qdrant 内部默认 k=60)
  → 交叉编码器重排 (BGE-reranker-v2-m3, candidates=20 → top_k=5)
  → 低分过滤（仅对 rerank 绝对分生效）
```

**最值得称道的设计是"分数量纲隔离"**（`qdrant.py:105`）：系统保留分数类型，**只对 rerank 分数使用绝对相关性阈值**，RRF / vector 量纲的分数直接跳过过滤。低分过滤参数：`score_abs_min=0.05`、`score_confident=0.5`、`score_rel_ratio=0.15`、`score_min_keep=1`（`config.py:93-97`）。

这解决了一个真实且常见的工程错误：RRF 输出的是 `1/(k+rank)` 量级的小数（约 0.016–0.03），若直接套用为 rerank 设计的 0.05 绝对阈值，**会把几乎所有结果误删**。作者不仅避开了这个坑，还在 `backend/tests/test_vector_relevance.py:14-77` 用纯函数单测覆盖了各分支（rrf passthrough / 绝对下限 / 相对断层 / 保底保留）。

**中文分词**（`qdrant.py:60-85`）：jieba 切中文段 + 正则保护英数串整体（如型号 `PS-12V-1.5A` 不被切开）+ Unicode 破折号归一化，**入库与查询对称调用同一函数**，避免两侧分词不一致导致的召回损失。这个细节体现了对 BM25 通道失效模式的正确理解。

⚠️ **一个静默降级风险**：`qdrant.py:53-54` 显示 jieba 未安装时 BM25 通道**直接用原文投喂，不报错**。后果是中文词面匹配能力显著下降，而检索指标可能看起来"还行"（dense 通道仍在），故障难以察觉。建议改为启动时显式告警或 fail-fast。

**版本可见性 fail-closed 已核实为真**：检索时构造 `should` 条件 —— `document_version_id` 为空 **OR** 在 `current_revision_ids()` 列表中（`qdrant.py:312-316`）；而 `current_revision_ids()` 在 PostgreSQL 不可用时 **`raise RuntimeError`**（`backend/app/vector/version_visibility.py:24-25`），不会返回空列表放行历史版本。`backend/tests/test_version_visibility.py:18-57` 用 Qdrant 内存模式验证了过滤生效、hybrid prefetch 与 outer filter 共享版本约束、注册表宕机时拒绝返回历史数据。**这是 README 声称与代码实现完全对齐的一项。**

### 3.3 Text2SQL：生成 / 校验 / 执行三分离

代码注释列出 9 步链路（`backend/app/analytics/text2sql.py:1-25, 178-309`）：

① 口径歧义前置检查 → ② Schema Linking → ③ Few-shot 检索（k=3）→ ④ LLM 生成 SQL → ⑤ guard AST 校验 → ⑥ EXPLAIN 预检 → ⑦ 只读事务执行 → ⑧ 失败则错误回灌重写 → ⑨ 结果转自然语言

> 实现细节：步骤 ⑥⑦ 在 `executor.execute()` 内部合并完成（先 explain 再 execute），对外表现为一步。

**四层 SQL 安全约束**，这是全项目最扎实的部分：

| 层 | 文件 | 实际约束 |
| --- | --- | --- |
| ① AST 白名单 | `analytics/guard.py:57-97` | 禁止 DML/DDL/事务控制语句；禁止 `pg_catalog`/`information_schema`/`pg_toast`/`pg_temp`；禁止约 25 个危险函数（`pg_read_file`、`dblink`、`pg_sleep`、`lo_import`、`set_config` 等）；禁止约 10 张系统表（`pg_shadow`、`pg_authid`、`pg_roles`） |
| ① LIMIT 强制 | `guard.py:163` | **外层包裹** `SELECT * FROM (original) AS _q LIMIT max_rows+1` —— 多读 1 行用于判定截断，且模型无法通过自己写更大 LIMIT 绕过 |
| ② 执行约束 | `analytics/executor.py:197-222` | `transaction_read_only=on`、`statement_timeout=5000ms`、`app.tenant_id` **无条件设置**（None → 哨兵值 `@anonymous@`），走独立只读角色 `kb_ro` |
| ③ 结果脱敏 | `analytics/redact.py` | 补充措施，非主边界 |
| ④ 数据库列权限 | `analytics/permissions.py:30-45` | 对 `kb_employee`：先 `REVOKE ALL` + `REVOKE SELECT(all cols)` + `REVOKE FROM PUBLIC`，再 `GRANT SELECT(allowed_cols)`，allowed = 全部列 − 敏感列 |

**第 ④ 层是整个安全模型的关键**，README.md:153 的论述完全正确：**"不能仅按输出列名脱敏：别名、表达式或整行转换可能改变结果列名，因此数据库列级权限才是关键边界。"** 而 `backend/tests/test_column_permissions_integration.py:71-96` 用真实 PostgreSQL 验证了**别名、表达式、`SELECT *`、`to_json` 整行转换均无法绕过列权限** —— 这个测试设计直击脱敏方案的根本弱点，质量很高。

**错误重写次数**：`sql_max_retry = 2`（`config.py:169`），即最多 3 次尝试（首次 + 2 次重写）。

### 3.4 多租户隔离：收敛为唯一入口

`apply_tenant_acl`（`backend/app/core/security.py:41-83`）的实现顺序是关键：**先 `merged.pop(settings.tenant_field, None)` 丢弃客户端传入的租户键（L79），再写入服务端认证的 `tenant_id`**。None/空串不注入。

这个"先丢弃后注入"的顺序消除了历史上两处实现导致的权限漂移（git `34aea09` 修复）。更重要的是，`backend/tests/test_agent_tenant_isolation.py:56-253` 不只测函数本身，还**穷举代码库所有 `retriever.search(` 调用点，断言只允许 2 个受控入口**，并强制两条通道共用 `apply_tenant_acl` —— 这是防止"后续新增入口遗漏权限传递"的结构性回归测试，比单点断言价值高得多。

PostgreSQL RLS 条件（README.md:166-170）：

```sql
USING (is_shared IS TRUE OR tenant_id = current_setting('app.tenant_id', true))
```

未设置租户身份时不能读取私有行，共享行仍按共享策略可见；执行器拒绝把保留哨兵值当作真实租户。

**配置前提与开发模式风险**：`auth_enabled` 取决于 `tenant_keys` 是否为空（`config.py:219-220`）—— 未配密钥时**完全匿名放行，`tenant_id=None`，不做任何租户过滤**。`validate_security()`（`config.py:305-325`）在 staging/production 强制：租户 Key 非空、`DEFAULT_ROLE=employee`、两个 analytics SQL 口令非空、`SQL_REDACT_COLUMNS` 非空、restricted SQL 用独立登录、禁止保留租户标识、角色必须已知。**这个"开发宽松 + 生产强制校验"的双轨设计是正确的**，但依赖运维正确设置 `ENVIRONMENT`。

### 3.5 版本化入库

流程（`backend/app/worker/tasks/versioned_ingest.py:15-70`）：

1. **暂存** — Document 记录 `status ≠ ready`，绑定 `document_key` + `file_hash`，版本文件不可变
2. **入库** — 获取 `lock(doc.document_key)` PG 行锁（L33）+ `SELECT FOR UPDATE` → `process_file` → `publish`
3. **发布** — `DocumentVersionRepository.publish(doc, automatic=True)` 在**同一事务内**（L59）
4. **并发** — 同一 `document_key` 通过 PG 锁串行化；重复投递检测 `status == ready` 直接返回（L25, L38-41）
5. **失败** — 异常时 `status = "failed"`（L66-69），**未完成版本不会替代当前版本**

`backend/tests/test_document_versions.py:41-348` 覆盖了版本去重、`asyncio.gather` 并发版本号单调递增、发布顺序回滚、数据库约束（两个 current / 缺 version）、worker 失败保留当前版本、重传幂等、删除清理可重试。覆盖面完整。

**分块策略**：
- 文本（`ingestion/chunking/text.py`）：`chunk_size=512`、`overlap=50`（`config.py:73-74`），段落 → 句子递归切分，Markdown 表格感知（大表按行切分并补表头）
- 表格（`ingestion/chunking/table.py`）：**行级语义化** `table_rows_to_sentences()` —— 逐行生成"ID 为 X 的员工，姓名为 Y…"完整句子，上限 `MAX_ROW_SENTENCE_ROWS=200` 行（L240）；XLSX/DOCX/PDF 共用；PDF 额外做宽表折行修复（`unwrap_wrapped_table_lines`）

行级语义化是为了让 embedding 能理解表格行的完整语义（而非孤立的单元格值），这是表格 RAG 的正确做法。但 200 行上限意味着**大表仍会被切断** —— 这正是引入 Text2SQL 的根本动因（见 4.1）。

**两个值得注意的实现细节：**

1. **SSE 用 `fetch + ReadableStream` 而非 `EventSource`**（`api/client.ts:101-102`），因为需要 POST body + `X-API-Key` 头，而 `EventSource` 只支持 GET 且不能自定义头。`consumeSse()` 共用解帧：`\n\n` 切帧 → `data:` 前缀 → `TextDecoder(stream:true)` 处理跨帧 UTF-8（`client.ts:172-198`）。这是正确选择。
2. **租户指纹防串会话**（`stores/chat.ts:33-39, 62-75`）：用 djb2 哈希 API Key 存入 localStorage，**Key 变更时自动丢弃旧 session** —— 避免切换租户后看到上一租户的对话历史。这个细节说明作者真实做过租户隔离演示并踩到过坑。

`AbortController` 刻意放在 state 外管理（`chat.ts:42`），避免被 Vue 响应式代理包裹。类型定义 `StreamEvent` 联合覆盖 10 种事件，与后端 `events.py` 一一对应（`api/types.ts:41-52`）。

nginx 对 SSE 的配置正确（`frontend/nginx.conf:28-34`）：`proxy_buffering off` + `proxy_cache off` + `proxy_request_buffering off` + `X-Accel-Buffering: no`，`proxy_read_timeout 3600s`，`client_max_body_size 50m`。

### 3.7 部署与运维

**Compose 服务链**（`docker_setting/docker-compose.yml`）：

```
qdrant → postgres(healthcheck) → redis(healthcheck)
       → migrate(一次性 alembic upgrade)
       → backend(depends_on: migrate completed_successfully)
       → worker(同镜像，不同 command)
       → frontend(depends_on: backend healthy)
```

用一次性 `migrate` 服务 + `completed_successfully` 条件保证 schema 先于 API 就绪，这是 Compose 下处理迁移的正确模式。backend/worker 共享 `knowledge_base` 与 `processed_cache` 卷（L69-71, L97-99）。worker 刻意关闭健康检查避免误判（L96）。

**CI（`.github/workflows/ci.yml`，3 个 job）** —— 设计意图在文件注释里写得很明确（L3-12）：**"把「评测 99%」从一次性结论变成持续保证"**。

- `backend-tests`：**刻意留空** `SILICONFLOW_API_KEY`，让需要真实 LLM/DB 的测试自动 skip 而非失败 —— "CI 不该依赖付费 API 与外部容器"（L50-56）。还跑评测器自检（`eval.quality_calibration`）与性能工具自检（`eval.performance --mode fixture`）并上传 artifact。
- `frontend-build`：`npm ci` + `vue-tsc --noEmit && vite build`
- `sql-guard`：**安全回归单独成 job**，理由写在 L133-134 —— "安全回归失败必须是**显眼**的，不能混在几百条单测里被忽略"

这个 CI 设计思路（hermetic 快测上云 + 真链路验证走本地 `-Full` 闸口 + 安全测试独立 job）在个人项目里属于超出平均水平的成熟度。

**`ops.yml`** 是定时运维任务示例，最诚实的一点在 L24-27：**"Action runner 上并没有你的 docker 环境与数据，因此本任务默认只做一次配置与脚本语法自检，不真连生产"**，并给出宿主机 cron / Windows 计划任务的真实执行方式（方式 B）。还附带监控接入建议（对账退出码 0/1/2 语义、备份要检查"是否真产生新文件"因为磁盘满时 pg_dump 可能"成功"写出 0 字节、三个关键 Prometheus 指标）与季度恢复演练步骤。

**本地三级门禁**（`scripts/check.ps1`）：L1 `compileall` 语法自检 → L2 `pytest -q` 全量单测 → L3（`-Full`）`eval --retrieval-only` + `eval.compare --baseline baseline_v1` 逐题回归。AGENTS.md 规定检索/分块/入库/评测改动必须跑 `-Full`。

### 3.8 评测体系

| 工具 | 作用 |
| --- | --- |
| `eval/runner.py:96-353` | 检索评测主入口：逐题 query → Recall@K / MRR / Source Rank / Keyword Hit Rate |
| `eval/compare.py:99-162` | **逐题回归比对**：按 question 建索引，比较 `recall_at_k` / `source_rank` / `passed`；聚合指标不得下降（容差 1e-9），**单题排名下降也判回归** |
| `eval/text2sql_runner.py` | Text2SQL 专项评测（支持 `--dry-gold` 只验 Gold SQL 可执行、不调 LLM） |
| `eval/quality_*` | LLM-as-judge 答案质量评判与校准 |
| `eval/performance*.py` | 请求级性能与用量采集 |

**逐题回归是这个评测体系最有价值的设计。** README.md:251 说明了动机：**"仅比较平均指标会掩盖「修好 A、退化 B」的情况。"** 检索质量优化中这是极常见的陷阱 —— 调一个阈值让平均分涨 0.5%，实际可能修好 3 题、搞坏 2 题。`compare.py` 把单题排名下降也算作回归，堵住了这个洞。仓库还刻意保留一条已知 miss，并要求"复现时应区分既有缺陷与新增回归"。

**历史基线**（`eval/baseline/baseline_v1.json`，已纳入版本管理）：107 题中 101 题参与判定（6 道 `no_knowledge` 题排除），100 题命中，**Recall@5 = 99.01%，MRR = 0.9703，rank_1 占 96 题**，retrieval-only 模式。

口径限定准确且反复强调：**"这是检索结果，不是最终答案正确率"**（README.md:23）、"来源命中口径，不证明片段完整或答案正确"（README.md:239）。

## 四、工程亮点评价

按"是否解决了真实工程难题"排序，我认为本项目的核心价值集中在以下五点：

### 4.1 用真实 badcase 驱动架构演进（最有说服力的一点）

Text2SQL 不是"因为流行所以加"，而是被一个具体错误逼出来的（README.md:51-70）：

| 指标 | 原纯 RAG 回答 | 数据库真值 |
| --- | --- | --- |
| Sales 人数 | 1042 | 1042 |
| Engineering 人数 | **25** | **1010** |
| 两部门差值 | **1017** | **32** |

错误差值 1017 vs 真值 32 —— 一个数量级的偏差。根因诊断也准确：**"万行表格切成多个片段后，即使召回片段高度相关，也无法证明覆盖了所有满足条件的记录。增加 top_k 或预生成少量摘要，仍无法覆盖任意筛选与分组组合。"**

这是 RAG 的**结构性局限**（相关片段 ≠ 完整数据），不是调参能解决的。项目的应对是把"检索相关证据"与"全量精确计算"分配给不同工具 —— 这个架构决策有明确的因果链和可复现的证据。而且 README.md:59 还主动限定："这是一例历史问题复现，不能据此推导全部问题的错误率。"

面试价值极高：它同时考察**问题定位能力**（为什么高分召回还是算错）、**方案选型判断**（为什么不是加大 top_k）、**边界诚实度**（不夸大）。

### 4.2 分数量纲隔离

见 3.2。RRF 分数与 rerank 分数是**两种不同尺度**，混用阈值会静默误删结果。多数 RAG 实现会踩这个坑且很难 debug（表现为"检索突然什么都返回不了"）。本项目显式保留分数类型、只对 rerank 用绝对阈值、rerank 失败退回召回排序时**不沿用 rerank 阈值**，并配纯函数单测覆盖分支。

### 4.3 安全边界落在数据库而非提示词

见 3.3 第 ④ 层。核心认知是：**结果脱敏按输出列名匹配是不可靠的**（别名、表达式、`to_json` 整行转换都能绕过），必须把权限下推到 PostgreSQL 列级 `GRANT`。而集成测试真的用这四种绕过手法去打，验证打不穿。

配合独立只读登录（`kb_ro` / `kb_employee` 两套账号）、RLS 行级隔离、只读事务、statement_timeout、外层 LIMIT 包裹，形成纵深防御。`README.md:151` 还留了一句清醒的话：**"SQL 解析器是其中一道防线，解析成功不等于语句安全或业务语义正确。"**

### 4.4 逐题回归 + 冻结基线

见 3.8。把"评测 99%"从一次性结论变成 CI 持续保证，且能检出"修好 A 退化 B"。这是**评测工程化**而非"跑过一次脚本"的分水岭。

### 4.5 fail-closed 的一致性

多个关键路径都选择了"不确定时拒绝服务"而非"降级放行"：

- 版本登记服务不可用 → `raise RuntimeError` 阻断检索，不放行历史版本（`version_visibility.py:24-25`）
- 租户身份为 None → 注入哨兵值 `@anonymous@`，RLS 下读不到任何私有行
- Agent 失败 → 降级到 RAG **但发送 `degraded` 事件告知用户**，不静默
- CI 中集成测试 → skip 而非假装通过，且 README.md:241 明确 **"跳过不能计为通过"**

git `34aea09` 的提交信息里专门写了 "fail-closed 迁移"，说明这是有意识的设计原则。

### 4.6 文档的自我批判性（罕见且可贵）

README 大量使用限定语主动削弱自己的结论，例如：

- "墙钟检查不能单独证明所有阻塞调用都在 60 秒内结束，仍需结合底层超时与真实测量"（L195）
- "轨迹展示的是工具执行事件，不能视为模型内部推理过程"（L211）
- "两个 PostgreSQL 数据库…业务只读账号与元数据库隔离，但这不等同于独立机器或独立集群的故障隔离"（L99）
- "以下为仓库中保留的历史基线或验收记录，**不代表每次代码修改后已重新取得同样成绩**"（L235）
- "工作流配置存在不等于当前提交已取得远端 CI 成功记录"（L294）
- 简历参考段落还特意提醒"以下表述需按个人贡献调整，不应写成已经生产上线"（L470）

`docs/经验教训.md` 存在且 git 历史显示持续更新（提交信息提到"20 条经验教训"）。这种"区分已验证 / 未验证"的写作纪律，在个人项目里非常少见。

### P2 — 已知能力缺口（作者已在 README 中登记，此处补充技术判断）

**6. 上传表格无法形成 SQL 闭环（最高优先级缺口）**

README.md:116 与 :226 已明确：**"API 上传的版本化表格只进入 RAG，尚不支持同步发布或回滚 Analytics 数据表。Text2SQL 演示数据需要单独装载，不能把「上传成功」理解为「已经可以对该表做 SQL 统计」。"**

这意味着当前 Text2SQL 能力**依赖手动跑 `python -m app.analytics.seed`**，不是产品化闭环。技术难点确实不小，需要解决：

- 租户表命名空间（避免跨租户同名表冲突 —— git `8ede0ac` 已经因为"表名归属保护"挡掉了跨租户物理删除，说明这个坑已经踩到）
- 发布/回滚与 Analytics 表的一致性（RAG 侧版本链已成熟，SQL 侧要对齐）
- Schema 元数据与 few-shot 示例的自动注册

这是从"演示项目"到"可用产品"之间最大的一道坎。

**7. 细粒度权限缺失**

只有租户级隔离 + 角色（employee/analyst），**没有文档级 ACL、部门级权限、内容分级**（README.md:227, :458）。实际企业里"同租户内不同部门看不同文档"是刚需。当前架构下补齐需要：Document 增加 ACL 字段 → `apply_tenant_acl` 扩展为多维过滤 → Qdrant filter 条件增加 → 检索评测集补充越权用例。

**8. 真实答案质量与容量数据完全缺失**

- 答案质量：评测框架已建（正确性/证据忠实度/引用/拒答四维 + LLM-as-judge + 12 道起始标注题），但 **"真实模型生成与评审尚未完成，暂无可信答案质量分数"**（README.md:244）
- 性能：只有本地合成基准，**"不代表生产容量、供应商费用或业务 SLO"**（README.md:245）

也就是说，项目能证明**检索召回准（99.01%）**，但**不能证明最终答案好**。这两者之间的鸿沟（检索对 ≠ 生成对）恰恰是 RAG 系统最难的部分。这是当前最该补的验证。

**9. worker 单并发**

README.md:461：worker 当前单并发；nginx 限制 50 MB 上传，但**直连 API 仍需补大小约束与内存治理**。大文档批量入库会排队，且 API 侧缺少上传体积限制意味着绕过 nginx 直连可造成内存压力。

**10. `/metrics` 端点未鉴权**

README.md:420 已标注：**"该端点未使用业务 API Key 鉴权，部署时应限制到监控网络；默认前端 nginx 仅代理 `/api/v1/`。"** 当前靠"nginx 不代理"作为唯一防线，属于配置层面的隐式防护。建议加内网 IP 白名单或独立监控 token。

**11. 前端类型安全局部失效**

`frontend/src/components/SourcesList.vue:3,8,21` 的 props 与内部函数使用 `any`，而 `api/types.ts:4-11` 已有严格的 `SourceItem` 定义（含 `document_version_id` / `document_version`）。`vue-tsc --noEmit` 在 CI 中运行，但 `any` 会让类型检查在该组件形同虚设。修复成本很低。

**12. jieba 缺失时 BM25 静默降级**

见 3.2。建议启动时检测并记录 WARNING，或直接在依赖里锁定 jieba 为必装项。

**13. Qdrant 物理快照故障未解决**

README.md:464：**"已有逻辑恢复证据，完整灾备仍待演练；Qdrant 物理快照故障尚未解决。"** 意味着向量库损坏时的恢复路径不完整 —— 需要重建索引（重新 embedding，有成本和时间开销）。

## 六、总体评价

**这是一个工程质量明显高于同类个人项目的实现。** 判断依据不是功能数量，而是以下几点：

1. **架构决策有因果链和可复现证据**，不是技术堆砌。Text2SQL 的引入由一个数量级的计算错误（1017 vs 32）驱动，根因诊断（相关片段 ≠ 完整数据）触及 RAG 的结构性局限。
2. **安全边界落在数据库层而非提示词层**，并且用真实的绕过手法（别名/表达式/`*`/`to_json`）写测试去打，验证打不穿。
3. **评测做到了逐题回归 + 冻结基线 + CI 持续保证**，能检出"修好 A 退化 B"，这已经越过"跑过一次脚本"的分水岭。
4. **fail-closed 在多个关键路径上保持一致**（版本登记、租户身份、Agent 降级、CI skip）。
5. **文档具备自我批判性**，主动区分已验证与未验证，不夸大结论。

**主要短板是"最后一公里"的验证与产品化**：检索准确率有硬数据（Recall@5 99.01%），但**真实答案质量、生产容量、成本三项核心指标全部空缺**；上传表格无法自动形成 SQL 闭环，细粒度权限缺失。项目自己的定位（"受控内部试点，尚未完成生产质量与容量验收"）是准确的。

**如果只推进三件事，我建议按此顺序：**

1. **跑通真实答案质量评测**（框架已就位，只差真实模型生成 + 评审 + 扩充标注题集）—— 这是把"检索准"升级为"答案好"的唯一路径，也是当前最大的证明缺口。
2. **清理工作区 + 修掉硬编码口令回退 + 同步过时数字** —— 成本极低，但直接影响可信度与安全性，且探针文件残留会污染检索评测。
3. **上传表格 → Analytics 同步发布** —— 工作量最大，但这是 Text2SQL 从"演示"变"产品"的必要条件。
