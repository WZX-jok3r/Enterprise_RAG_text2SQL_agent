# 从零读懂企业知识库 Agent：代码导读与面试手册

本文基于当前工作区的 `backend/app/` 与 `frontend/src/` 静态阅读整理。它解释实际代码路径，区分实现、设计意图和待验证事项，不把注释或历史指标当作当前运行证据。建议先读第 1—6 节建立流程，再读权限、并发与评测，最后用自测题检验理解。没有一份题库能覆盖所有面试问题；目标是掌握能够推导新问题的机制。

## 1. 先学会用自己的话介绍项目

30 秒版本：

> 这是一个多租户企业知识问答助手。非结构化文档用混合检索 RAG 找依据，结构化数据用只读 SQL 做精确统计，Agent 根据问题决定调用哪些工具。FastAPI 提供接口，Vue 展示答案和执行事件，ARQ 处理异步入库，PostgreSQL 管理会话、任务和文档版本，Qdrant 保存向量，Redis 提供会话缓存与队列。

2 分钟版本应补上三个设计原因：

1. 文档检索返回的是相关片段，不能保证覆盖全表，因此统计交给 SQL。
2. 模型输出不能被信任，因此租户身份来自服务端，SQL 经过语法、执行、账号和数据权限约束。
3. 模型行为有不确定性，因此编排需要预算、执行事件、测试与评测，而不是只写提示词。

项目没有训练一个大模型。它调用外部模型，主要工作是数据处理、检索、工具编排、安全和工程验证。简历应按实际个人贡献描述。

## 2. 六个先弄懂的概念

| 概念 | 通俗解释 | 在项目中的位置 |
| --- | --- | --- |
| LLM | 根据 messages 生成文本或工具调用 | `llm/provider.py`、`llm/tool_client.py` |
| Embedding | 把文本映射到数值向量，便于相似性搜索 | `vector/embedding.py` |
| Chunk | 供索引与检索使用的一小段文本，带来源元数据 | `ingestion/chunking/base.py` |
| RAG | 检索外部证据，再放入模型上下文生成答案 | `rag/pipeline.py` |
| Text2SQL | 将自然语言问题转成 SQL，由数据库计算 | `analytics/text2sql.py` |
| Agent | 根据问题和工具结果决定下一步动作 | `agent/loop.py` |

Embedding 不是压缩后可以无损还原的文档，也不是生成答案的模型。Reranker 对“问题+候选段落”联合评分，适合精排少量候选。LLM 的模型参数没有因为上传文件而更新；更新的是外部知识索引或业务库。

学习任何模块时都问：输入是什么？输出是什么？会读写什么？信任谁？失败怎样处理？哪条测试能证明它？

## 3. 系统分层、进程与数据地图

### 3.1 分层不是目录好看，而是责任不同

```text
浏览器组件 → Pinia Store → HTTP/SSE 客户端
                         ↓
FastAPI 路由 → 身份/服务依赖 → Service / Agent / Pipeline
                                  ↓
                       Repository / 检索 / SQL / 模型客户端
                                  ↓
                     PostgreSQL / Redis / Qdrant / 文件 / 模型服务
```

- 路由负责 HTTP、请求校验、依赖、状态码和 SSE 包装。
- Service 负责业务流程、事务和资源协调，例如先写文档记录再入队。
- Repository 负责具体数据查询与锁，不负责 HTTP。
- Agent 负责选工具、收观察和形成答案，不直接操作所有数据库细节。
- RAGPipeline 负责检索、上下文和生成的组合，不重复实现向量召回。
- Client 负责外部服务协议、调用、重试和序列化。

这里不是每个模块都严格走 Route→Service→Repository。Agent 和 RAG 属于问答编排，analytics 中也有同步数据库访问，不能把分层图讲成绝对规则。

### 3.2 API 与 worker 是两个进程

API 处理在线请求，worker 从 Redis 领取入库任务。共享的是 PostgreSQL、Qdrant、Redis 和挂载文件，不是 Python 对象或内存变量。单例也只能是某个进程内的复用对象，不能跨 worker 或跨容器共享。

### 3.3 数据放在哪里

| 数据 | 存储 | 原因 |
| --- | --- | --- |
| 文档原文件、不可变版本副本 | `knowledge_base/` 与 `.versions/` | 可以重新解析、追踪版本和恢复 |
| 文档身份、版本、状态、当前指针 | PostgreSQL `rag` 的 documents | 用事务、唯一约束与锁管理业务状态 |
| 会话、消息、tool_context | PostgreSQL `rag` | 持久化事实来源 |
| 入库任务、SQL 审计、模型用量、表结构元数据 | PostgreSQL `rag` | 状态与追溯 |
| 业务表行 | PostgreSQL `kb_analytics` | 用 SQL 做全量计算，配置独立权限 |
| dense/bm25、段落原文、来源和租户 payload | Qdrant | 搜索时需要向量与过滤条件 |
| 最近会话消息 | Redis List | 热缓存，丢失可回源 |
| ARQ 作业及队列状态 | Redis | 异步调度；丢失不能靠会话回源恢复 |
| 前端当前消息与状态 | Pinia | 页面渲染，不是持久化事实来源 |
| API Key、session ID 等 | 浏览器 localStorage | 当前演示方案；不能视为企业身份系统 |

两个 PostgreSQL 数据库默认在同一实例上，逻辑与账号隔离不等于独立集群故障隔离。

## 4. 从启动入口读起

入口：[main.py](../backend/app/main.py)。`uvicorn app.main:app` 导入模块级 `app`，它由 `create_app()` 创建。

`create_app()` 注册中间件、API 路由、异常处理和可选指标端点。`lifespan` 在启动/关闭时初始化或释放数据库、Redis 和 ARQ 连接池。模型与部分检索依赖通过懒初始化取得，避免所有资源都在模块导入时立即连接。

配置：[config.py](../backend/app/core/config.py)。Pydantic Settings 把字符串环境变量转换成配置类型。本地读取根 `.env` 与 `backend/.env`，后者可覆盖前者，环境变量也参与配置；Compose 通过 `env_file` 注入并覆盖服务地址。

数据库：[database.py](../backend/app/database.py)。

- Engine 管理连接池和数据库方言，不等于一条永久占用的连接。
- Session 是一次数据访问/事务的工作单元，不应被并发请求共同修改。
- `async_sessionmaker` 创建短会话，service 决定提交边界。
- `flush()` 将变更发送到数据库，不等于 `commit()`；提交才结束成功事务。
- `expire_on_commit=False` 避免提交后访问 ORM 属性自动触发重新加载，不能解释成禁用事务隔离。
- Alembic 管理演进，`create_all()` 不能替代升级已有数据库的迁移。

依赖：[deps.py](../backend/app/api/deps.py)。`Depends(get_principal)` 让路由获得身份，`Depends(get_session_service)` 获得服务。测试可以覆盖依赖，不必真连全部服务。`get_db()` 使用 `yield`，让资源退出时关闭；事务提交不是依赖自动替所有业务完成的。

**健康检查边界：** 当前 `/health` 是存活探针。启动时数据库/Redis 探活失败仅记录告警，不一定阻止 API 启动。因此 HTTP 200 不证明问答与入库已经可用，需要独立 readiness。

## 5. 完整走一遍文档问答

问题：“整机质保多久？”这里先用经典 `/chat/stream` 讲清 RAG 本身。

### 5.1 前端到路由

[chat.ts](../frontend/src/stores/chat.ts) 根据模式发起请求。Store 先添加用户消息与空 assistant 占位，收到事件后原地更新。

[client.ts](../frontend/src/api/client.ts) 使用 fetch POST，请求头携带 API Key。它读 `ReadableStream`，用 `TextDecoder(..., {stream:true})` 处理分段 UTF-8，再缓冲并按空行解析 SSE。一个网络包可能有半帧、多帧或半个汉字，不能把每次 `read()` 当作完整 JSON。

[chat.py](../backend/app/api/v1/chat.py) 执行：

```text
解析 Principal
→ 复用本租户有效 session，否则新建
→ 读取进入本轮前的历史
→ 先存本轮 user
→ 构建服务端租户 filter
→ 调用同步 stream_chat 生成器
→ 通过线程池桥接，转换为 SSE
→ 收到 done 后保存 assistant，并附 session_id
```

先取历史再存本轮 user，避免当前问题在模型 messages 里出现两遍。

### 5.2 Pipeline 不是向量搜索实现

[pipeline.py](../backend/app/rag/pipeline.py) 的 `stream_chat()` 调 `_retrieve()`，后者调用 [Retriever.search](../backend/app/rag/retriever.py)。Retriever 是薄封装；真正的搜索在 [VectorStore.search](../backend/app/vector/qdrant.py)。

当前搜索顺序：

```text
读取 PostgreSQL 当前版本登记
→ 构造版本约束 AND 租户/业务过滤
→ 问题 Embedding
→ dense 与 BM25 分别召回
→ Qdrant RRF 排名融合
→ Rerank
→ 按 score_kind 过滤低相关结果
→ 返回 chunks 与 dropped
```

读取版本登记发生在问题 Embedding 之前。登记不可用时停止检索，避免未知版本参与回答，也避免在这条失败路径中继续发送问题到 Embedding 服务。

### 5.3 一个检索结果大致长什么样

以下为结构示意，不是某次真实请求抓包：

```json
{
  "text": "【文档: warranty_policy.md】\n整机质保两年……",
  "score": 0.83,
  "score_kind": "rerank",
  "metadata": {
    "source": "warranty_policy.md",
    "format": "md",
    "document_version_id": "123",
    "document_version": 2,
    "tenant_id": ["tenantA"]
  }
}
```

tenant payload 可是数组；Qdrant 用单租户 MatchValue 匹配数组中的成员。source 是显示来源，版本文件还保留 storage_source，不能把显示文件名与物理存储名混为一谈。

### 5.4 模型怎么得到文档

[context_builder.py](../backend/app/rag/context_builder.py) 把文本拼成 `【参考1】来源…`，附页码、行号、Sheet 等元信息。[prompts/rag.py](../backend/app/prompts/rag.py) 的系统提示包含这个 context。最终 messages 由 system、历史和本轮 user 构成。

模型生成时读的是检索文本，不是直接登录 Qdrant。引用是来源格式与提示词形成的输出，仍需要评测是否真实支持回答，不能把“有来源列表”当成“每个陈述都有证据”。

### 5.5 返回哪些 SSE 事件

```text
meta：来源与数量
→ delta：多次文本增量
→ done：完整答案与会话信息
```

实际帧类似 `data: {"type":"delta","text":"质保"}\n\n`。HTTP 头发送后，流中错误一般通过 `error` 事件反馈，不能再随意把 HTTP 状态改为 500。因此判断成功应检查结束事件，而非只看 HTTP 200。

**重要差异：** `query()` 没召回会直接返回拒答；`stream_chat()` 也在没有 chunks 时结束；`query_with_history()` 会用“无相关参考资料”继续调用模型。当前各入口的拒答语义不完全相同。

## 6. 检索背后的算法与取舍

### 6.1 Dense 与 BM25 为什么互补

“售后期限”和“质保多久”词不相同，语义向量可能更容易匹配；“PS-12V-1.5A”这样的型号，精确词面匹配很重要。两条通道没有谁总是更好，需要同一业务题集比较。

dense collection 配置使用 cosine。向量相似度衡量表示空间中的接近，不直接衡量答案正确、权限合法或事实完整。Qdrant 的索引实现与近似搜索参数属于服务端配置，需要实际查看部署，不能从应用封装推断已调优。

BM25 可理解为词频、词稀有程度与长度归一化共同评分。更罕见的业务词通常更有区分度，重复词不会无限线性增加分数。项目通过 Qdrant 的 `qdrant/bm25` 与 IDF modifier 使用这条能力，中文预分词在 `tokenize_for_bm25()`，不是手写一个完整 BM25 服务。

### 6.2 为什么是 RRF

概念公式：`融合分(d) = Σ 1 / (k + rank_i(d))`。这个 k 是融合常数，不是最终 top_k；未出现的文档在相应列表不贡献分。

dense 和 BM25 的原始分数范围不同，直接相加需要校准。RRF 用名次融合，降低跨分数量纲问题，但也损失原始分数差距信息。项目调用 `FusionQuery(fusion=Fusion.RRF)`，具体常数以服务端实现为准。

两条 prefetch 与外层查询使用同一个过滤约束。这样候选在召回阶段就受限，比先召回全部租户再应用层过滤更能保持可见候选的召回配额。

### 6.3 召回与重排不是一件事

- prefetch_k：每个召回通道取多少候选。
- rerank_candidates：进入融合后待重排列表的目标规模之一。
- top_k：最终返回给上层的条数上限。

增大候选可能提高召回，也增加延迟与重排成本；增大 top_k 会增加生成上下文和干扰。没有“越大越好”的结论。

Embedding 可预先计算文档向量，而交叉编码器需要同时读问题与段落，适合少量精排候选。项目重排外呼失败会回退原始召回排序，这意味着可用性保住了，质量保证降低了。

### 6.4 低相关过滤不能共用一个阈值

`_filter_low_relevance()` 只对 rerank 分数量纲生效。RRF 是排名融合分，cosine 是向量相似度，rerank 是模型相关性输出，都不是已校准的“答案正确概率”。

当前过滤有两段：最高分很低时，根据 `score_drop_all_below` 全丢或保底；最高分足够高时，用绝对下限与相对断层共同过滤；中等分簇主要用绝对下限。具体阈值应通过标注题集调节。

这里的 dropped/hidden_count 是低相关过滤数量，不是“被权限拒绝的文档数”；没有权限的向量早就在查询过滤阶段排除了，不能据此泄露或统计他人文档。

### 6.5 99.01% 怎么来的

当前冻结基线以“期望来源文件是否出现在前 5 个结果中”判定，101 道参与题中 100 道命中：`100/101 ≈ 99.01%`。107 总题中 6 道无知识拒答题不进入这个分母。

MRR 是首个正确来源名次倒数的平均，未命中贡献 0。首位是 1，第二位是 1/2，第五位是 1/5。MRR 高说明正确来源通常更靠前，不能证明返回片段完整。这个来源命中口径也不同于对全部相关 chunk 计算的标准多相关项 recall。

## 7. 结构化问答的两条真实代码路径

入口：[agent.py](../backend/app/api/v1/agent.py)。规则函数：[router.py](../backend/app/agent/router.py)。状态机：[loop.py](../backend/app/agent/loop.py)。

### 7.1 规则路由

`route_by_rules()` 返回 RouteDecision，包含目标、原因和命中词。

- 命中文档意图且没有同时构成“聚合词+字段词”时，走 RAG。
- 聚合词和字段词共同命中时，走 SQL。
- 其余交给模型选择。

仅凭“最多”不能路由 SQL，“最多多久吃一次”可能是文档问题。规则是确定函数，可通过表驱动测试验证。

当前主入口调用的是默认字段词表。虽然有 `build_column_words()` 从 schema 构造词表的辅助函数，但不能说入口已经自动接入全部动态字段，也不能说已建立完备意图分类器。

### 7.2 强制 SQL 路径：自然语言交给 Text2SQL 引擎

```text
AgentLoop.run()
→ _run_forced_sql()
→ list_data_tables()
→ _exec_sql_via_engine()
→ AgentTools.sql_answer(question)
→ Text2SqlEngine.answer(question, 元数据 session, tenant, redact)
→ _finalize()
```

`sql_answer()` 是内部工具封装，不是暴露给模型的第四个工具 schema。

[Text2SqlEngine.answer](../backend/app/analytics/text2sql.py) 的步骤：

1. 先检查客单价、增长率等口径歧义。
2. 从 `rag` 读取 AnalyticsTable/AnalyticsColumn 元数据，过滤身份不允许看到的字段。
3. 用词面相关性选择相关表，渲染数据字典。
4. 从本地 question-SQL 示例库检索 3 个 few-shot；受限身份排除涉及敏感字段的示例。
5. 调模型生成 SQL 或澄清动作。
6. 执行 guard 校验和改写。
7. 执行器做权限预检、EXPLAIN、实际查询、序列化、审计。
8. SQL 无效时把错误和上一条 SQL 反馈给模型，有限次重写；默认 `sql_max_retry=2` 意味着首次加两次重写，最多三次生成尝试。

Schema Linking 在这里主要是轻量词面打分和裁剪；Few-shot 使用中英 token 重叠及结构信号，不是向量示例检索，也不是微调模型。`schema.py` 注释中提到可缓存，不代表当前函数已建立 Redis schema 缓存。

### 7.3 自动 Agent 路径：模型直接给 SQL

```text
build_messages()
→ chat_with_tools(messages, TOOLS)
→ 模型产出 tool_calls
→ dispatch("sql_query", {sql: ...})
→ AgentTools.sql_query(sql)
→ guard + executor
→ observation 回灌模型
→ 模型继续选择工具或回答
```

这个路径不自动调用 Text2SqlEngine 的 few-shot、自修正和歧义规则。它通过整个 Agent 循环处理工具观察，不能说两条 SQL 路径完全相同。两者共享的是 SQL 安全与执行层。

用户问“先查制度，再看业务数据是否符合”时，模型可以选择多个工具，但需要实际数据和评测验证跨源结论。

## 8. SQL 网关到底做了什么

核心文件：[guard.py](../backend/app/analytics/guard.py)、[executor.py](../backend/app/analytics/executor.py)、[permissions.py](../backend/app/analytics/permissions.py)。

### 8.1 为什么不用正则判断 SELECT

`SELECT` 可以包含危险函数、子查询、系统表、写入性结构，字符串前缀不足以表达语法。AST 是语法树：节点表示选择、表、列、函数等，可以遍历结构。

guard 当前解析 PostgreSQL 方言，检查单语句、根节点、子树中的禁止类型、危险表/schema/函数，并检查部分结构完整性。它不是把所有业务表动态做成完备授权白名单；某些合法 SQL 形状也会被保守拒绝，需查测试与具体 AST。

**三个不同判断：** 可解析 ≠ 可执行 ≠ 业务语义正确。sqlglot 解析器不能独自证明安全，EXPLAIN 能发现表列与类型问题，但不能证明用了正确统计口径。

### 8.2 LIMIT 为什么多一行

假设业务上限是 200。guard 外包查询读取最多 201，执行器 `fetchmany(201)`：

```text
读到 200 行：不能据此认为有更多，truncated=false
读到 201 行：至少还有第 201 行，返回前 200，truncated=true
```

如果 guard 先把上限设为 200，执行器永远看不到第 201 行，截断检测就失效。外层包装也能压住模型自己写的更大 LIMIT；它限制返回行数，不保证内部扫描、排序或聚合便宜，需要数据库超时与性能治理。

如果模型本来写了更小 LIMIT，外层无法发现更小 LIMIT 之前的全集；truncated 仅表达本系统上限导致的截断，不能证明业务查询本身覆盖全量。

### 8.3 EXPLAIN 与实际执行

不带 ANALYZE 的 EXPLAIN 检查数据库能否规划查询；EXPLAIN ANALYZE 会实际运行，所以不能拿它做“不执行”的预检。项目分别建立预检和执行连接，并在每条路径设置权限相关会话参数。

`set_config(name, value, true)` 的第三个参数使设置限于当前事务，避免连接池复用时保留上个租户身份。用绑定参数传租户值，不用字符串拼接身份。应用发起的 set_config 是可信内部操作；模型 SQL 中的 set_config 则被 guard 禁止。

### 8.4 四层约束回答的是不同问题

| 层 | 主要回答 |
| --- | --- |
| AST | 模型写了什么形式的 SQL？是否包含禁止操作？ |
| 只读事务与超时 | 这次查询如何执行、持续多久？ |
| 数据库账号与列授权 | 这个连接实际有权限读写哪些对象/列？ |
| RLS、角色与结果处理 | 哪些行/字段对这个身份可见？ |

敏感字段不仅是输出问题：`WHERE salary > ...`、`ORDER BY salary`、`AVG(salary)` 即使不返回原始列，也可能泄露信息。当前应用层检查 Column 引用，受限账号的列授权提供数据库兜底。不能只把 salary 改成 NULL，也不能只隐藏 schema。

默认 analyst 可以访问敏感列，employee 使用另一登录。当前执行器通过非空 `redact` 集合选择受限登录；这个实现与敏感配置联动，所以 staging/production 要求敏感列配置非空并验证账号不同。权限模型尚不是按用户、部门、每表每列单独制定的完整企业策略。

Decimal、日期等需转成 JSON 友好类型。当前 Decimal 转 float/int，对高精度金额可能损失精度；若要求财务精确展示，应考虑 Decimal 字符串与统一前后端格式。

## 9. Agent 的“智能”和“控制”如何配合

模型只输出函数名和参数，Python 程序通过 dispatch 真正执行工具。Function Calling 不是模型获得任意代码执行能力。工具描述和 JSON schema 帮助模型生成参数，但服务端仍要校验、限权。

`ToolOutcome` 将三类信息分开：

- observation：模型继续判断的文本。
- summary：前端简要轨迹。
- payload：SQL、rows、sources 等结构化结果。

AgentLoop 对象进程内复用，`run()` 每次新建 AgentState。不能把 seen_calls、上一轮结果、actor 放在共享 loop 的可变字段上，否则并发会串请求。

### 9.1 为什么五步、八次和六十秒不是全部硬保证

五步限制自动决策循环；八次主要统计编排层模型调用；Text2SQL 自身生成与 HTTP 重试并不全部计入这个数字。六十秒在步骤边界检查，单个同步模型请求可有更长底层超时，强制路径也没有完整 deadline 传播。因此不能承诺“绝不会超过六十秒”或“最多付费八次”。

去重键用工具名加排序后的参数 JSON，防止字典键顺序不同误判。它挡住完全重复调用，不能阻止改一个字符不断试探；还要依赖总预算、速率与权限约束。

### 9.2 当前 Agent 的流式范围

`_finalize()` 最后 `yield ev_delta(answer)`，发送的是完整答案。自动循环用非流式 `chat_with_tools()`。因此当前主要是**工具事件流式**，不等于最终答案逐 token 生成。`llm/tool_client.py` 虽有 stream_chat 能力，不代表主 AgentLoop 已使用它。

### 9.3 降级要看具体分支

模型异常、所有工具失败、重复调用等可触发 RAG 路径。达到最大步数时设置降级事件并进入收尾，不是每个异常都自动重试 RAG；强制 SQL 错误也可能直接作为失败观察返回。

可用性降级与答案可靠性不同。统计问题回退文档检索，可能重新遇到局部数据问题；更合适的后续策略是保守拒答、展示失败或只提供文档依据。

## 10. 文档上传、解析与分块

入口：[documents.py](../backend/app/api/v1/documents.py)。服务：[ingestion_service.py](../backend/app/services/ingestion_service.py)。任务：[ingest.py](../backend/app/worker/tasks/ingest.py)。

### 10.1 为什么 API 返回 202

202 表示请求已接受，不表示索引完成。解析大 PDF、批量 Embedding、写向量都可能较慢，留在请求里会占用连接和资源。API 保存文件与任务后返回 task_id，前端轮询 PostgreSQL 里的状态。

当前接口一次性 `file.read()`，nginx 有 50 MB 限额，但直连 API 没有同等后端限制。异步入库不等于上传本身没有内存风险。

### 10.2 解析与分块分开

[loader.py](../backend/app/ingestion/loader.py) 把文件转换成 Document 文本与元数据；[chunking](../backend/app/ingestion/chunking/) 再按内容类型生成 Chunk。这样解析方法可以替换，分块策略也可独立调整与测试。

- 普通文本优先按段落/句子，过长才做大小切分与 overlap。
- Markdown 按标题与段落，遇到表格保持结构。
- 表格过大按行拆，每个子块补表头；还有行级语义化，将一行改写成可检索字段关系。
- PDF 需要考虑文本层、版面、表格和扫描件 OCR；DOCX 也可能有表格和图片。
- OCR 是可选依赖与系统能力，不能声称 Docker 默认已经全部安装。

当前通用 `chunk_size` 常以 Python 字符串长度衡量，不是 tokenizer 精确 token 数。不同语言、表格和元信息前缀会改变最终 token 体积。

overlap 降低边界信息丢失，也增加索引大小、重复召回和成本。表头补全解决行列对应关系，但不能使一个片段覆盖整表统计。parent_id/table_id 元信息也不能独自证明已实现检索后的完整父块扩展。

### 10.3 indexer 加了什么元数据

[process_file](../backend/app/ingestion/indexer.py) 执行解析→分块→向量写入，并可在文本前注入显示文件名，提高点名问某份文档时的词面区分度。

版本分块携带 document_version_id、document_key、document_version、version_chunk_index 等；租户列表写入 payload。修改前缀或分块策略会改变索引文本和 point ID，评测必须与相应索引同步，不能只改代码不重建就评价效果。

## 11. 版本化：为什么不能上传时直接删旧数据

文档“质保政策.md”从 v1 更新到 v2，若先删 v1 再开始做 v2 Embedding，中途失败就没有可用版本。当前设计是先 staging，新版本完成后再切当前指针。

相关文件：[版本仓储](../backend/app/repositories/document_version_repo.py)、[版本任务](../backend/app/worker/tasks/versioned_ingest.py)、[可见性](../backend/app/vector/version_visibility.py)。

### 11.1 三种身份不要混淆

- document_key：租户和规范化原文件名构成的逻辑文档标识。
- Document.id：一个物理版本记录的数据库主键。
- version：这个逻辑文档链的编号，例如 1、2、3。

文件内容 hash 用于完整性与有限去重。reserve 仅比较最新版本的相同内容及状态，不是全库任意内容去重。同名不同租户形成不同逻辑链。

### 11.2 状态与发布

```text
pending → 解析与向量写入 → ready
    └────────异常──────→ failed
ready + is_current=true：当前发布版本
ready + is_current=false：历史就绪版本
deleted：逻辑隐藏，外部数据待清理或已清理
```

文档状态与任务 queued/running/done/failed 是两套状态，不能混为一谈。ready 也不一定是 current。

版本 worker 校验任务与版本/租户绑定、文件 hash，按 document_key 取事务 advisory lock，再锁版本行，执行索引；成功后在数据库事务中设置 ready、发布指针并更新任务。

已有 ready 版本被重复投递时不重新发布，避免重试把用户回滚撤销。自动发布不允许较旧完成版本覆盖较新 ready 版本。API 激活还会检查同链 pending/failed 版本，未完成版本需先完成或删除。

### 11.3 数据库约束是最后一道一致性防线

Document 上有 `(document_key, version)` 唯一约束，current 必须是 ready 的检查约束，以及 `WHERE is_current` 的部分唯一索引，使同一链最多一个当前版本。

部分唯一索引只约束符合条件的记录；否则普通 unique(document_key) 会阻止历史版本共存。

### 11.4 Qdrant 与 PostgreSQL 没有跨系统事务

先把版本向量写到 Qdrant，只有数据库 current 指针发布后才能召回。这个模式实现的是受登记控制的发布可见性，不是 PG+Qdrant 的分布式原子事务。

失败可能残留隐藏的 staging 向量，需要重试、对账与清理。查询构造“未版本化 legacy OR 当前已发布 ID”，再 AND 租户过滤。登记不可用则拒绝检索。

查询读取 current ID 后若发生回滚/删除，该在途请求不一定立即切换；版本可见性是读取登记时的决定，不是跨所有系统的实时快照。大量 current ID 列表未来也需要规模优化。

版本删除先把 PostgreSQL 标为 deleted 并取消 current，再清向量和文件。外部清理失败仍保持隐藏并可重试。当前版本删掉后不会自动选另一个历史版本，需显式激活。

### 11.5 为什么看到 ingest.py 的 SQL 同步不能下结论

旧入库路径有 analytics 同步。但当前 API 上传携带 version_id，`ingest_document()` 一开始就转到 `ingest_version()`，后者明确跳过 SQL 发布。所以“旧代码有同步”不等于“当前 API 上传已经同步”。这是读实际调用链比读设计注释更重要的例子。

## 12. 会话持久化、缓存与并发

[SessionService](../backend/app/services/session_service.py) 先按 PostgreSQL 校验 session 归属，再读 Redis；miss 时从 PostgreSQL 取最近消息并回填。读缓存不能跳过权限校验，因为 session ID 不应当被当作凭据。

Redis 使用 List，追加 RPUSH、LTRIM 最近 N 条、EXPIRE 续期。TTL 是缓存键有效期，当前服务不能据此宣称 PostgreSQL 旧会话自动清理。Redis 丢数据可回源，但 Redis 完全不可用时，当前缓存操作缺少普遍的异常降级，问答仍可能失败。

### 12.1 seq 的经典竞态

```text
事务 A 读 max(seq)=10
事务 B 读 max(seq)=10
A 插入 seq=11
B 也插入 seq=11 → 唯一约束冲突
```

[SessionRepository.lock_session](../backend/app/repositories/session_repo.py) 用事务级 advisory lock，在同一事务内保护取 seq、插入和更新时间。不同 session 使用不同锁键，哈希碰撞主要导致不必要串行。

不应说“FOR UPDATE 没办法实现”：锁尚不存在的 Message 行无效，但可以锁已存在的 ChatSession 行，这是替代方案；当前选择 advisory lock，配合真实数据库竞态测试。

### 12.2 这把锁保护了什么，没保护什么

它保护一次消息追加的 seq 分配，不锁住整轮问答。两个标签页可能同时取到同一段历史，并交错写 user/assistant。数据库 commit 后的 Redis append 也不在同一个分布式事务里，提交顺序与缓存顺序可能不同；miss 回填也可能与并发 append 竞争。

因此不能把“seq 没冲突”讲成“整个多轮问答已经线性一致”。未来可以加入会话轮次 ID、每会话串行调度、版本化缓存或基于 DB seq 的重建策略。

### 12.3 tool_context 是能力，也是一份敏感数据

Agent 保存有限 SQL 和结果行，下一轮自动路径的 build_messages() 注入最近六条消息的 tool_context。它不是完整长期记忆，也不保证所有路径都读到同一历史。

强制 SQL 的 sql_answer() 当前未向 Text2SqlEngine.answer 传入会话 history，强制收尾也主要使用本轮观察；自动 raw SQL 路径的结果未在 `_exec_tool()` 中写入 executed_sql/rows。因此不能宣称所有 SQL 路径的追问记忆都完全覆盖。

SQL audit 不保存结果集，不代表整个系统不保存结果：messages.tool_context、答案和缓存都可能含已授权查询内容。角色降权后旧数据如何处理仍需设计。

## 13. async、线程池和资源预算

`async def` 不是把同步 requests、解析器和 SQL 调用自动变成非阻塞。事件循环只在可等待操作处让出执行；直接调用同步 I/O 会卡住其他协程。

项目把同步 Pipeline/Agent 用 `run_in_threadpool` 或 `iterate_in_threadpool` 桥接，入库用 `asyncio.to_thread`。同步生成器调用 `next()` 时才执行到下一次 yield，桥接需要将这一步放线程池。

这解决事件循环阻塞，不保证无限并发，也不能消除 Python CPU 运算的 GIL 约束。瓶颈还可能是线程池、数据库池、供应商限流、CPU、内存或 Qdrant。

worker 当前 max_jobs=1，一份长文件会使后续任务等待。版本任务在持锁事务中进行外部索引，能简化同链并发与删除竞态，但长时间占数据库连接和锁；扩大并发前要考虑 lease/fencing、分阶段发布与失败恢复。

客户端 AbortController 取消的是浏览器请求，不保证正在运行的同步模型外呼被中断，也不证明停止计费。需要把取消与剩余 deadline 传播到下游。

## 14. 重试与失败策略

[retry.py](../backend/app/core/retry.py) 对连接错误、超时及部分 429/5xx 做指数退避加抖动；多数确定性 4xx 不重试。attempts 是总尝试次数，不是首次之后再试多少次。

三种重试不同：

| 重试 | 解决的问题 | 风险 |
| --- | --- | --- |
| HTTP 重试 | 上游暂时超时/限流 | 重复调用费用、等待叠加 |
| SQL 自修正 | 生成了不存在的列或错误结构 | 模型仍可能写出业务语义错误 |
| ARQ 任务重执行 | worker 作业失败/再投递 | 重复向量写入、状态回退与副作用 |

不是所有上游调用都用同一重试策略：非流式完成、Embedding、Rerank 有重试封装，经典 LLM 流式实现不能一概说已安全重试。流式输出中途重新生成会导致重复文本或不一致，需明确恢复语义。

版本向量 ID 包含版本 ID、chunk 序号和文本，重试清的是本版本，不删除当前其他版本。这是有限幂等设计，不是 exactly-once。相同任务不会永远只执行一次，应按可能重复执行设计。

服务数据库 commit 与 enqueue 不在一个事务。版本提交失败会显式标记状态并报 503，仍可能有进程在 commit 后、enqueue 前崩溃的窗口；生产可考虑 transactional outbox 和补偿对账。

## 15. 可观测、评测、备份要分开讲

### 15.1 可观测回答“发生了什么”

- trace ID 把同一次请求的日志和指标关联。
- Counter 看请求、失败、拒绝、降级次数。
- Histogram 看延迟分布，不只看平均。
- 请求级性能采集通过 ContextVar 隔离收集器；文件锁只保护进程内写入，多进程要另行汇合。
- metrics.py 是进程内状态，多进程下不能直接当作全局准确累计值。

Langfuse 是可选集成，未启用返回 no-op。启用后可能记录 prompt、上下文和输出，和仅记录数值的 performance ledger 是不同数据路径；不能宣称所有遥测均不含内容。

SQL elapsed_ms 主要统计执行阶段，不等于自然语言到答案的总延迟，也不一定含 EXPLAIN。总链路还包括身份、会话、Schema、模型生成、重试、检索和答案组织。

### 15.2 评测回答“结果是否达到目标”

| 类型 | 证明的东西 | 不证明的东西 |
| --- | --- | --- |
| 纯逻辑单测 | 输入输出、分支、不变量 | 真正供应商、数据库与部署行为 |
| 数据库集成 | 事务、RLS、列授权、锁 | 所有企业业务语义 |
| 检索评测 | 当前题集来源命中与排序 | 答案正确、事实忠实 |
| SQL 评测 | 与题目期望结果的执行比较 | 任意新 schema 的泛化 |
| 答案质量评测 | 正确性、证据忠实、引用、拒答 | 未覆盖题型的质量 |
| 性能评测 | 指定流量与配置下延迟/吞吐/失败 | 不同硬件、索引和供应商下的容量 |

当前检索基线是 107/101 的历史记录；Text2SQL 历史 42/42 仅四表范围；2026-11-11 本机全量回归为 745 passed/147 skipped（合计 892）。真实验收数字带日期，不能当作本手册重新跑出的结果；真实答案质量与生产容量尚未建立可信基线。

测试跳过不是通过。带模型的某些 E2E 断言允许瞬时基础设施失败，适合守语义回归，不能拿全部绿色替代稳定成功率。小题集需警惕题型单一、示例泄漏、数据分布和过拟合。

逐题回归比较能发现聚合指标掩盖的“等量置换”。最终上线仍需代表业务的新题、权限题、无答案题、冲突版本题和攻击题。

### 15.3 性能成本常见口径

TTFT 是到第一个非空文本 delta，不是到 route/meta 事件。当前 Agent 工具事件先出来并不证明文本首段快。P95 看成功和全请求分布、失败率及样本量，20 个样本不足以稳定估计尾延迟。

性能 runner 是 closed-loop：客户端请求完成后再发下一条，系统越慢，发出的 QPS 越低，因此不等同于固定到达率的突发容量测试。

成本公式可概括为 `(输入 token×输入单价 + 输出 token×输出单价)/100万`，但必须覆盖每次尝试、价格模型、流式 usage 完整性。缺失 usage/价格是未知，不是 0；按请求计费的模型不能套 token 单价。还需要后台入库、基础设施与账单对账。

### 15.4 备份恢复回答“坏了能否回来”

只备份 PostgreSQL 不够，还需要业务库、向量与 payload 索引、原文件、角色权限、配置及任务队列策略。多个组件没有共同快照时，需停写窗口或一致性编排。

已有 PG 与逻辑向量/文件隔离恢复证据；Qdrant 物理快照、新主机环境、Redis 队列及服务切换仍待验收。备份文件存在不等于可恢复，恢复行数相同不等于 ACL、索引、序列及业务引用都正确。

## 16. 看源码时发现的边界：面试不要替代码夸大

下列均是静态阅读结果，未在本轮复现，不应作为新增缺陷已验收的结论。

| 观察 | 对外表述 |
| --- | --- |
| Agent `_finalize()` 一次发完整 delta | 工具过程流式，最终答案尚非逐 token 流式 |
| 主路由使用默认词表 | 已有动态词表辅助函数，主入口未完整接入 |
| Text2SQL 强制路径不传 history | 不保证该路径全部多轮澄清/指代能延续 |
| `_exec_tool()` 未保存 raw SQL 结果到跨轮轨迹 | 自动 SQL 路径记忆覆盖仍需补齐 |
| 强制 SQL listing 在 `_exec_tool()` 后又 append，强制 SQL 轨迹可能重复记录 | 当前计数/轨迹存在重复记录风险，要测试核实，不能拿数字作为完整工作量证据 |
| 最大步数收尾的 `_compose_answer()` 主要看 forced_observation | 不保证用尽步数后综合所有自动工具结果 |
| `get_vector_store()` 返回新 VectorStore，而不是缓存单例 | 上层 Pipeline/Tools 的复用不能推导每个 factory 都是单例 |
| AgentTools._session() 默认创建新同步 Engine | 连接池复用和生命周期需优化，不能声称所有连接均统一管理 |
| Schema 元数据在 tenant=None 时不加租户过滤 | 开发匿名路径不能等同于生产隔离；数据执行 RLS 与 schema 可见性要分别评估 |
| 消息 DB 锁不覆盖 Redis append 和整轮对话 | 已解决 seq 竞态，不等于所有会话并发一致性问题解决 |
| 旧入库包含 SQL 同步、版本化路径跳过 | 当前 API 上传仍只进 RAG |
| 权限校验与敏感集合、独立登录联动 | 需要正确生产配置和真实授权测试 |

面试被指出不足时，可以说明当前保护范围，给出更完整的设计及验证方法。不要把未来方案说成已经实现，也不需要为了讲项目临时替换代码。

## 17. 如何定位一次错误回答

按链路排查，不从“再写一段 prompt”开始。

1. 确认请求模式、租户、角色、session、索引和版本。
2. 看 route 是否符合预期，规则命中哪些词。
3. RAG：是否有期望来源？是否是正确片段？是否被过滤？排序是否异常？context 是否缺关键段？
4. SQL：Schema 是否包含所需表列？权限是否合理？SQL 的筛选、分组、单位、时间范围、去重、NULL 语义是否正确？
5. 看数据库结果是否正确，然后看模型转述是否改变了事实。
6. 区分失败、截断、降级与真正无数据，不能把所有空结果都称为知识库没有。
7. 保存可重现的获准夹具，加入对应回归，再调整策略并逐题比较。

SQL 没有报错仍可能口径错；检索分数高仍可能资料冲突或不完整。问题可能出在源数据、解析、分块、召回、重排、上下文、路由、SQL、权限或答案组织，不只在模型。

## 18. 设计变更时如何回答追问

| 假设问题 | 先检查什么 | 可考虑的方案，均不代表当前已实现 |
| --- | --- | --- |
| 文档增加百倍 | 当前向量数、过滤选择性、候选规模、尾延迟 | 索引参数、按知识域过滤、检索缓存、评测规模扩充 |
| 多人同时问同一会话 | seq、轮次、缓存顺序、历史快照 | 每会话串行、轮次 ID、乐观版本与幂等请求 |
| 表增加到上百张 | Schema 裁剪与关系依赖 | 检索相关 schema、保留 join 路径、语义指标层 |
| 知识库有冲突文件 | 版本、权威等级、日期、引用 | 冲突提示、业务权威规则、人工确认 |
| 模型被文档注入诱导 | 文档是否当指令、工具权限 | 不可信证据隔离、模型前后校验、攻击评测；权限必须独立生效 |
| 要上传任意表立刻统计 | 租户表身份、DDL、版本发布 | staging SQL 表、统一发布指针、补偿对账、受限登录授权 |
| 要减少成本 | 调用场景、重试、token、rerank | 缓存、候选裁剪、模型分级、共享计算；缓存键必须含权限与版本 |
| 要多 worker | 内存指标、文件日志、池大小、锁 | 合并遥测、资源预算、任务幂等、锁粒度和租约 |
| 要更换 Embedding | 维度、语义空间、评测 | 新集合重建、双索引验证、受控切换，不直接混用新旧向量 |

设计题回答顺序：目标与规模→现有瓶颈证据→方案→取舍→失败模式→如何验证。没有数据时说“需要先测”，比虚构百万级支撑更可信。

## 19. 面试自测：60 个问题与回答锚点

以下是回答方向，不是逐字背诵稿。每题都应能指出相关函数、例子或测试。

### 项目与架构

1. **项目解决什么问题？** 文档依据与业务统计同时存在，分别使用 RAG 和 SQL，Agent 组织调用。
2. **与调用一个聊天 API 有何不同？** 数据处理、索引、权限、工具、会话、版本、验证与运维。
3. **为什么没训练模型？** 目标是让现有模型使用私有、可更新证据；微调不能直接保证事实新鲜或权限。
4. **为什么手写 Agent？** 当前三工具、分支有限、需复用协议和测试；复杂审批或工作流会改变选择。
5. **为什么两个业务进程？** 在线问答与耗时入库生命周期和资源需求不同，队列解耦。
6. **为什么多个存储？** PG 管状态/计算，Qdrant 管检索，Redis 管缓存/队列，文件保留原件。
7. **数据库隔离到什么程度？** 两个库、不同账号，同一默认 PG 实例，不是独立集群。
8. **一个请求怎么走？** 从 Store、client、路由、Principal、会话、编排、工具到 SSE 和持久化。

### RAG 与数据处理

9. **RAG 和微调怎么选？** RAG 管外部事实，微调偏行为/格式；不能说互相完全替代。
10. **为什么混合召回？** 语义改写与型号词面匹配互补，用题集做对照。
11. **RRF 为什么不直接加分？** 原始分数量纲不同，以名次融合，代价是丢分差信息。
12. **Rerank 与 Embedding 区别？** 独立向量可预计算，联合编码评分更贵但适合精排。
13. **top_k 越大越好吗？** 召回收益与延迟、上下文、干扰及费用权衡。
14. **为什么要中文分词？** 让稀疏词面匹配更有区分度，并保持查询/入库处理对称。
15. **chunk_size 是 token 吗？** 当前许多分块用字符长度；不能等同 tokenizer token。
16. **overlap 为什么存在？** 保留边界信息，增加重复与成本，需评测选择。
17. **怎么处理表格？** 按行分块、补表头、行级语义化；统计仍走 SQL。
18. **怎么处理扫描 PDF？** OCR 可选路径与系统依赖，需验证镜像环境和识别质量。
19. **文件名为什么放进文本？** Qdrant BM25/rerank 主要看文本，帮助点名区分相似文档。
20. **低相关阈值怎么定？** 按 score_kind 和题集调，不能当作答案正确概率。
21. **rerank 失败会怎样？** 降级原召回顺序，质量可能降低，不沿用 rerank 阈值。
22. **幻觉如何减少？** 证据、无知识拒答、冲突处理、生成约束和质量评测，不能保证清零。
23. **多轮问答会改写 query 吗？** 当前经典检索主要用本轮 query，历史参与生成；不能声称已有完善查询改写。
24. **Recall@5 和 MRR 证明什么？** 来源命中与首位排序，不能证明答案或统计完整。

### Agent 与 SQL

25. **模型如何调 Python？** 产出工具名与 JSON 参数，服务端 dispatch 执行，模型不直接执行。
26. **规则会不会误判？** 会；聚合+字段信号、文档意图优先和表驱动测试降低风险。
27. **强制 SQL 和自动 SQL 有何不同？** 前者 Text2SqlEngine，后者模型直接 SQL，共享 guard/executor。
28. **Schema Linking 当前怎么实现？** 词面打分、元数据裁剪，不是复杂关系图推理。
29. **few-shot 是训练吗？** 请求时注入相似问答 SQL 示例，未修改权重。
30. **SQL 能执行就正确吗？** 可能时间、单位、去重、join 或聚合口径错，需结果真值评测。
31. **什么时候澄清？** 指标存在多定义且缺限定，规则和模型显式动作；注意路径覆盖差异。
32. **SQL 自修正怎么做？** SQL+校验/执行错误回灌，最多有限次生成；不是随机重复原请求。
33. **为什么不用字符串过滤 SQL？** 嵌套语法、函数和系统访问要看 AST，数据库权限仍兜底。
34. **为什么 SELECT 也危险？** 系统表、敏感聚合、危险函数和资源消耗。
35. **LIMIT 解决所有性能问题吗？** 只限制输出，不限制所有扫描/排序/聚合工作。
36. **为什么读 N+1 行？** 确认系统上限造成的截断，guard 和 executor 必须配合。
37. **EXPLAIN 与 ANALYZE？** 前者规划，后者实际执行，预检不能误用。
38. **五步八次六十秒是否硬上限？** 编排范围控制，内部重试与阻塞调用不完全覆盖，需传播预算。
39. **Agent 是否逐 token 流式？** 当前工具事件流式、完整答案最后 delta；经典 RAG 才逐段转发。
40. **降级一定安全可靠吗？** 不一定，统计退回 RAG 要避免局部数据冒充全量事实。

### 安全、一致性与可靠性

41. **谁决定 tenant_id？** 服务端认证 Principal，丢弃模型/客户端过滤中的租户覆盖。
42. **过滤何时生效？** Qdrant 两通道及融合外层，SQL RLS，应用文档/任务/会话归属。
43. **RLS 为何 fail-closed？** 未设身份不能匹配私有行，共享按策略允许；账号不可绕过 RLS。
44. **连接池如何防串租户？** 每次设置身份，事务级 local 作用域，分别覆盖预检/执行。
45. **脱敏够不够？** 别名、WHERE、排序、聚合能绕过输出名策略，数据库列授权更关键。
46. **API Key 角色是不是用户 RBAC？** 当前主要租户级两角色，非完整用户/部门/文档权限。
47. **版本更新为什么不先删旧？** staging 完整后发布，失败不损当前可用版本。
48. **版本发布有没有分布式事务？** 没有，PG 指针控制可见性，隐藏残留需补偿。
49. **重试会撤销回滚吗？** ready 作业重复投递不重新发布；晚到自动任务也防覆盖新 ready。
50. **怎样保证仅一个 current？** 同链锁、事务更新、部分唯一索引和 ready 检查约束。
51. **缓存丢失与缓存故障是否相同？** miss 可回 PG；完全不可用仍可能报错，需异常降级。
52. **seq 锁保护整轮问答吗？** 只保护追加事务，跨轮并发与缓存顺序还需设计。
53. **为什么事务 advisory lock？** 结束自动释放、粒度按会话；锁 ChatSession 行也是替代。
54. **ARQ 是否 exactly-once？** 不能承诺，按重复投递设计幂等与副作用。
55. **浏览器停止是否停止供应商计费？** 不保证，同步调用可能继续，需下游取消机制。
56. **async 能解决 CPU 瓶颈吗？** 不直接；线程池、GIL、多进程/原生库和资源上限分别考虑。

### 评测与上线

57. **892 例测试全过就能上线吗？** 745 通过 + 147 跳过，mock 与集成证明范围不同，仍需质量/容量/运维验收。
58. **如何测并发费用？** 明确流量、硬件、模型、完整延迟/TTFT、错误、重试、usage 与价格覆盖。
59. **怎么证明恢复成功？** 验证两库、向量、索引、文件、权限、引用和业务运行，测 RTO/RPO。
60. **下一个最值得补什么？** 上传表格与 SQL 版本闭环、细粒度 ACL、真实质量/容量基线；按岗位选择重点。

## 20. 七次学习任务：从听懂到能自己讲

### 第一次：画图

只看 main、config、deps、models，手画进程和存储。自测：Qdrant 和 PG 各存什么？worker 与 API 为什么共享文件？配置在哪生效？

### 第二次：追一条经典 RAG

看 frontend Store/client→chat.py→pipeline→retriever→qdrant→LLM，逐个写输入输出。自测：租户在哪注入？meta 和 delta 谁发？历史何时读？

### 第三次：追 SQL

看 router→forced SQL→text2sql→schema/fewshot→guard→executor。给一条合法 SQL、一条敏感派生 SQL、一条大结果查询，解释每一层处理。

### 第四次：读 Agent 分支

手写自动循环的伪代码，解释工具消息配对、seen_calls、made_progress、finalize。对比自动/强制 SQL，标出不同 budget 和 history 范围。

### 第五次：追版本

看 upload→reserve→enqueue→ingest_version→publish→current_revision_ids。分别推演断网、部分写入、重复任务、回滚、删除和并发上传。

### 第六次：用测试验证理解

先在隔离的合成数据环境读测试再决定运行，避免碰生产或真实外部模型。重点：SQL guard、tenant isolation、version visibility、session concurrency、Agent loop。看断言真正证明的事情，特别是反证竞态测试。

### 第七次：模拟面试

用 2 分钟介绍项目，随后从第 19 节随机选 10 题。每题回答“机制、取舍、证据、边界”。被追问未来方案时明确说“计划/可考虑”，并说明验证方法。
