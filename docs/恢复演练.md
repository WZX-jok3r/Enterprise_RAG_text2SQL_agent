# 恢复演练

本次完成了本地 PostgreSQL、Qdrant、知识库文件和解析缓存的隔离恢复。演练不覆盖线上数据，不调用外部模型。每一阶段校验通过后才进入下一阶段，失败返回非零退出码，报告不标记成功。

## 本次真实结果

- PostgreSQL：`rag` 的 10 张表、`kb_analytics` 的 4 张表，恢复后逐表比较行数与全行内容 SHA-256，包括会话、消息、文档、入库任务、审计及用量。
- Qdrant：`personal_rag` 1154 个点、`personal_rag_v2` 1402 个点；比较全部点 ID、原始 dense/sparse 向量和 payload。逻辑恢复另外验证向量配置与 payload 索引。
- 文件：知识库原文件（含 `.versions`）和 `processed_cache`，逐文件 SHA-256 比对。
- 物理快照失败：两份快照上传恢复均返回 HTTP 500。快照内 WAL `first-index` 为全零字节，源文件是有效 JSON。根因尚未定位，不能把物理快照标记为可恢复。
- 为此补充独立逻辑备份：导出原始向量、payload 和索引配置，不依赖重新调用 Embedding。逻辑恢复经过实际验证。
- 第一轮失败报告保留在 `output/recovery_drill_20261009/report.json`；重试报告在 `output/recovery_drill_20261009_retry/report.json`；仅凭备份包恢复报告在 `output/recovery_saved_bundle_20261009/report.json`。
- 重试备份约 95.854 秒，恢复及核验约 137.225 秒（包含尝试失败的物理快照）。这是本机组件耗时，不是生产服务 RTO；未模拟故障时间点，未测 RPO。

## 运行完整演练

从 `backend` 目录执行，选择一个尚不存在的输出目录：

```powershell
..\.venv\Scripts\python.exe -m app.analytics.recovery --output ../output/recovery_new
```

演练使用当前设置连接本地服务，通过 PostgreSQL 容器内 `pg_dump -Fc` 导出。创建随机 `recovery_<uuid>` 数据库和集合，恢复至这些新资源，比较内容，再删除本次创建的数据库和集合。备份包与恢复文件保留供复核。清理失败同样判定演练失败，报告列出需要处理的资源。

开始前应确保没有上传、删除、版本切换、SQL 写入或其他后台任务。跨 PostgreSQL、Qdrant、文件系统没有共同事务快照；脚本前后比较源数据发现变化即失败，生产备份仍需正式停写窗口或一致性编排。本次没有停止正在运行的服务。

## 只使用已保存的备份包

```powershell
..\.venv\Scripts\python.exe -m app.analytics.recovery --bundle ../output/recovery_drill_20261009_retry/bundle --output ../output/recovery_saved_new
```

此入口先检查所有文件的清单和 SHA-256；通过后在全新随机数据库和集合恢复。它使用备份中的 `inventory.json`、PG dump、`points_*.json`、`qdrant_config.json` 和文件目录，不读取源集合或原文件。恢复目标仍是隔离资源，验证后清理，不会直接切换正在运行的 API。

常规备份入口 `python -m app.analytics.backup --keep 7` 已补齐快照下载、逻辑向量、原文件和校验清单。组件失败不会触发旧备份清理；清理仅处理时间戳命名且具有清单的备份目录，`--keep` 必须大于零。常规备份的清单格式也可交给上述 `--bundle` 入口演练；本次实际演练使用的是 recovery 入口生成的包。

## 故障恢复顺序

1. 暂停上传和 worker；建立全新 PostgreSQL/Qdrant 目标。密钥从密钥管理系统恢复，备份不包含 `.env`。本次使用同一 PostgreSQL 实例，已有角色仍在；新实例必须先建立应用账号和 `kb_ro`、`kb_employee`，使用项目 `setup_db` 的角色配置恢复权限。PG dump 不包含全局角色。没有演练新主机部署或角色重建。
2. 验证清单后恢复两个 PG 库；确认迁移版本、表结构、约束、租户与版本状态。演练比较内容，但不等于验证所有 ACL、DDL 和 sequence 属性。不可在未经验证的备份上直接执行生产覆盖式恢复。
3. 使用已验证的逻辑向量备份恢复 Qdrant，创建 payload 索引。按集合比对所有点及向量、payload；物理快照路径暂不可作为唯一恢复手段。此工具适用于当前单节点配置，不包含多节点协调及 collection alias 恢复。
4. 恢复知识库目录，保留 `.versions` 的路径与文件名；检查文件哈希。知识库版本登记与向量版本必须来自同一停写备份窗口。
5. Redis 会话热缓存从 PG 回源，避免恢复过期热缓存覆盖事实数据。**不要 FLUSHALL 生产 Redis。** Redis 也承载 ARQ 队列，丢队列不会自动恢复未完成任务。启动 worker 前查询：

```sql
SELECT id, document_id, tenant_id, status
FROM ingest_tasks WHERE status IN ('queued', 'running');
```

逐项核对文档是否已 READY、文件是否存在与哈希是否匹配，再决定重试或标记失败。不能直接批量重放所有旧任务；已恢复的队列也可能重复投递。本次未执行队列重放、Redis 故障注入或生产 Redis 清空。

6. 在隔离环境通过租户权限、会话回源、版本可见性与检索检查，再切换配置、恢复 API 与 worker。涉及真实模型的问答烟测需要相应数据外发授权，本次没有执行。

## 备份与报告边界

备份包包含企业知识文件、会话及业务数据，尽管不含 `.env`，仍应加密、限制访问并保存异地副本；项目 output/backups 是本地演练产物，不能抵御本机磁盘损坏。SHA-256 用于发现文件损坏，未签名清单不能防止恶意同时篡改清单与数据。当前向量导出在内存排序，适用于本项目规模；大数据量需流式导出、分片校验和独立存储。

不要将这次结果表述为“生产全链路容灾已完成”：已验证的是隔离组件恢复和保存备份的独立逻辑恢复，物理快照故障、新主机角色部署、Redis/队列恢复、线上切换及业务 RTO/RPO 仍需后续演练。
