# 请求状态与权限边界修复

本次改动针对 Agent 请求串线、文档租户边界、SQL 敏感字段绕过和生产配置默认放行。

## 请求隔离

- AgentLoop 只保存工具、模型客户端和运行配置；工具观察、待发来源信息全部进入每次调用的 AgentState。
- 统计与工具上下文由该次调用的 done 事件携带，不再从全局 last_stats/last_tool_context 读取。
- `_tool_context` 是内部传递字段，API 持久化后移除，不进入浏览器 SSE。
- 回归测试刻意暂停租户 A，让租户 B 在同一个实例上完整执行后恢复 A，同时验证答案、来源和轨迹归属。

## 文档边界

- 上传使用完整 UUID 作为物理文件名前缀。
- 文档去重查询增加 tenant_id，避免相同 source/hash 更新其他租户登记行。
- 删除向量同时约束 source 与登记记录的 tenant_id；客户端不能指定删除过滤器。
- 存在其他文档登记引用同一物理文件时保留该文件，保护历史同名记录。

## SQL 权限

- analyst 使用原 kb_ro 只读账号；权限受限的查询使用独立 kb_employee 登录与连接池。
- kb_employee 无角色成员关系、无 BYPASSRLS、无整表 SELECT 或未来表的默认 SELECT；只授予允许列。
- 初始化在一个事务内收敛角色和现有列权限。新表建表时同步授予允许列。
- SQL AST 预检拒绝敏感列的显式引用，包括别名、表达式、聚合、WHERE、ORDER BY、CTE。
- PostgreSQL 列权限阻止 SELECT *、整行 JSON 和解析器漏网引用；不依赖返回列名。
- EXPLAIN 与执行使用相同的受限账号、租户变量和事务护栏；账号或授权缺失时失败，不退回特权连接。
- Schema 给普通员工隐藏敏感列。敏感字段所在列名在其他表中也按保守策略限制。
- 原来的结果列名脱敏仍保留为补充。涉及敏感字段的查询现在可能直接拒绝，而非返回姓名和掩码。

## 部署升级

在原有环境配置中增加：

```dotenv
ANALYTICS_EMPLOYEE_USER=kb_employee
ANALYTICS_EMPLOYEE_PASSWORD=<独立口令>
```

启动 PostgreSQL 后，在 backend 目录执行：

```powershell
..\.venv\Scripts\python.exe -m app.analytics.setup_db
```

该命令会创建受限登录、收敛已有授权，并更新现有表的列权限。随后重启 API/worker。
调整 SQL_REDACT_COLUMNS 后也必须重新执行授权初始化。未初始化时，普通员工 SQL 失败关闭。

production/staging 额外要求：RAG_TENANT_KEYS 非空、DEFAULT_ROLE=employee、两个 SQL 账号均设置口令、受限账号与特权账号分离。
分析员通过 RAG_TENANT_ROLES 显式授权。API 与 worker 启动及身份解析都会校验。
开发环境保留原来的匿名调试与默认角色行为。

前端不再读取 VITE_RAG_API_KEY，Docker 构建也不再内置演示 Key；通过界面的运行时设置填写 Key。
本次没有修改用户的实际 .env，也没有执行在线数据库授权更新。

## 范围

本次 SQL 列级授权不自动转换成文档级权限：若敏感内容也出现在用户获准读取的 PDF/XLSX 等文档中，仍需后续文档 ACL 与数据分级治理。
API Key 仍是租户级身份，本次没有引入用户级 OIDC，也没有处理已有会话在角色降权后的历史内容撤回。
数据库角色和表权限依赖受信任的部署管理员；本次未宣称覆盖任意自定义 SECURITY DEFINER 函数。
