# 并发、延迟与成本测量

新增`python -m eval.performance`，测量query、chat、chat-stream和agent-stream的HTTP完整延迟、流式首段文本延迟、吞吐、失败与降级。新增请求级数值记录关联所有普通RAG、Agent、Embedding及Rerank调用尝试，包括模型内部重试；检索、版本登记查询和SQL执行提供阶段耗时。

## 指标口径

| 指标 | 定义 |
| --- | --- |
| 客户端并发 | 固定数量的异步worker；完成一个请求再发下一个 |
| observed_peak_inflight | 客户端实际在途请求峰值，不表示服务器执行线程数 |
| 完整延迟 | 请求发出至响应体完整接收，包括服务端排队、网络、重试和流式生成 |
| TTFT | 请求发出至第一个非空文本delta到达；meta、工具事件不算文本 |
| P50/P95/P99 | nearest-rank分位数，同时保留样本数；分别统计全请求和成功请求 |
| successful_rps | 成功请求数 / 当前档位测量墙钟时间；另列attempted_rps |
| error_rate | HTTP错误、超时、业务错误、SSE错误或缺少结束帧 / 全部测量请求 |
| degraded_rate | Agent显式degraded事件或最终degraded标记 / 全部测量请求 |
| trace_coverage | 与服务端数值记录关联成功的请求比例 |

这是closed-loop压测，不能直接模拟固定到达率或承诺突发容量；请求本身变慢时，客户端发出的QPS也下降。工具不主动重试失败请求；模型网关本身的每次重试分别记账。失败及超时不会从统计分母消失，HTTP200也不能掩盖SSE错误。该工具验证响应协议与错误状态，答案正确性仍由答案质量评测负责。

阶段耗时可能重叠：retrieval包含版本登记查询、Embedding和Rerank，不能把这些P95相加作为总延迟。客户端平台信息是压测机信息，生产对比还必须记录服务端CPU/内存、worker数、线程/连接池大小、文档规模和模型配置。

## 第一步：验证工具（不调用外部模型）

在backend目录执行：

```powershell
..\.venv\Scripts\python.exe -m pytest tests/test_performance_metrics.py tests/test_performance_capture.py tests/test_performance_runner.py -q
..\.venv\Scripts\python.exe -m eval.performance --mode fixture --endpoint chat-stream --requests 20 --concurrency 1,2,4,8 --warmup 2 --output ../output/performance_fixture_baseline.json
```

fixture启动临时localhost TCP服务，使用真实FastAPI路由、同步线程池和SSE，但模型与会话使用合成依赖。固定模型等待时间约15ms，token也是夹具数据；不用Qdrant、Redis、企业知识库或付费API。服务在执行结束后关闭。此模式用于验证测量工具和接口调度，不能作为生产RAG容量、真实模型首token延迟或实际费用。

本次四档各20个请求，共80个测量请求及8个预热请求，全部成功且用量关联覆盖率100%。原始记录为`output/performance_fixture_baseline.json`，摘要为同名`.md`，服务端数值记录为`.measurements.jsonl`。20个样本仅适合小规模验证，尾延迟稳定性需要更长的、代表实际流量的测量。

## 第二步：开启真实请求记录

API环境配置中设置绝对路径并重启：

```dotenv
PERFORMANCE_LOG_FILE=D:/PythonProjects/personal_rag/output/performance_usage.jsonl
```

默认关闭。启用时仅记录request_id、HTTP状态、结束状态、耗时、模型标识、token及异常类型，不保存题目、答案、上下文、APIKey或错误原文。纯ASGI中间件不会为了采集数据缓冲SSE。通过现有`X-Request-ID`关联客户端与服务端记录；账本写入失败不阻断回答，但报告中成本覆盖率会下降，金额不能假定为0。

本轮已验证单进程记录及线程池隔离。多worker部署应各自输出独立文件，通过日志系统按request_id汇合后提供合并JSONL；进程内文件锁不等于跨进程锁。记录为追加写入，应使用专用文件并安排轮转，不能让压测期间文件截断破坏关联。

当前采集范围是在线HTTP问答；后台入库worker的Embedding成本、基础设施费用和供应商账单对账尚未纳入。本地基准包含数值采集开销，不能直接和关闭采集的基准混用。

## 第三步：显式价格与成本覆盖

复制`eval/data/performance_prices.example.json`填写真实来源、日期、版本及价格。示例的空rates表示尚未提供价格，不表示免费。每条价格的格式为：

```json
{
  "kind": "llm",
  "model": "实际返回的模型标识",
  "input_per_million": "实际每百万输入token价格",
  "output_per_million": "实际每百万输出token价格"
}
```

kind可为llm、embedding或rerank，同一模型标识和kind只能出现一次，金额非负且使用Decimal计算。公式是`(输入token × 输入单价 + 输出token × 输出单价) / 1,000,000`。这里仅支持token计价；按请求/文档计价的模型需要另外实现计价单位，不能硬填一个token单价。

- `known_cost`是已观测且有价格部分的估算金额，不能视作完整账单。
- `total_cost`仅在记录完整、所有调用用量及价格已知、流式调用完整时提供；否则为null。
- `cost_measured`、`cost_warmup`和`cost_including_warmup`分别列出测量、预热和两者合计，避免预热调用被漏记。
- `cost_per_attempted_request`与`cost_per_successful_request`只在测量成本完整时给出；后者把失败请求产生的费用也摊到成功请求，预热单独列出。
- 缺少usage的失败调用可能已经产生费用；缺少usage或价格保持未知。失败返回明确usage时，已有用量参与估算。
- 流式usage按最后一次累计值记录，不把每帧累计token再相加；中断后的局部usage不能证明完整费用。

金额是按显式价格表的估算，尚未处理不同缓存计价、优惠、税费或账单差异。最终实际支出仍需与供应商账单核对。本次没有提供真实模型价格表，因此夹具报告的金额为null。

## 第四步：小样本真实验证通过后升压

先准备仅含id、question、top_k的JSONL，格式见`eval/data/performance_cases.example.jsonl`。通过环境变量`RAG_BENCH_API_KEY`指定压测租户的运行时Key，不在CLI参数或报告中保存密钥。真实问答会把题目和检索片段发送给配置的模型服务，需具备相应数据发送授权；本轮没有再次执行该外部调用。

```powershell
..\.venv\Scripts\python.exe -m eval.performance --mode http --base-url http://127.0.0.1:8000 --endpoint chat-stream --dataset eval/data/performance_cases.example.jsonl --requests 1 --concurrency 1 --warmup 0 --usage-log ../output/performance_usage.jsonl --prices ../output/performance_prices.json --require-cost --output ../output/performance_smoke.json
```

只有小样本通过后再运行更长的多档测量，SLO数值必须由项目目标确定。例如约定了完整延迟和首段延迟上限后，分别提供`--max-p95-ms`与`--max-ttft-ms`。工具每档完成后检查闸口，失败便停止升压并保留已有报告；`--require-cost`还会阻止在成本覆盖不完整时继续。

默认可靠性闸口为0错误率，也要求预热全部成功；默认不臆造延迟SLO。没有require-cost时，成功的延迟测量可以通过，但金额仍为null，不能据此宣称成本测量已完成。`complete`表示所请求档位及所选择闸口已全部完成，应同时检查各成本条目的complete与trace_coverage。

退出码：0表示所选闸口通过；1表示可靠性或延迟闸口未通过；2表示输入/记录无效或所要求的成本覆盖不完整。报告保留逐请求数值，可复核失败、TTFT、全请求尾延迟和分阶段耗时。不同模型、价格、流量、运行配置或硬件不能直接当作同一性能基线。

CI已经接入本地夹具自检及报告上传，不调用付费API；真实SLO与成本闸口由有授权的本地/专用环境执行。

本次验证结果：新增21项测量测试全部通过；后端全量750项通过、19项真实模型测试因明确禁用外部调用而跳过。四档本地夹具基准和报告完整性检查通过，语法检查及`git diff --check`通过。CI配置已更新，尚未在GitHub上运行；真实模型容量和费用尚未测量。
